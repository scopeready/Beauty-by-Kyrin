# SEO Strategy — Beauty by Kyrin

**Site:** www.beautybykyrin.com · **Live** on the `beauty-by-kyrin` Vercel project
**Prepared:** 2026-09-18 · **Companions:** `KEYWORD-RESEARCH.md`, `KEYWORD-MAP.md`, `COMPETITOR-RESEARCH.md`, `LOCAL-SEO-GEO-PLAN.md`, `CONTENT-INVENTORY.md`

> **Two warnings that govern this whole document.**
>
> **1. No rankings are guaranteed — by me, by this document, or by anything in the codebase.** Search engines and answer engines rank what they choose to rank. Everything below is a set of decisions that make the site *easier to rank and easier to quote*. None of it is a promise of position, traffic, a rich result, a map-pack slot, or an AI citation. Treat any prediction of a specific ranking as false.
>
> **2. There is no measured search-volume data behind the keyword targets.** Ahrefs returned `Insufficient plan` on every endpoint including the free one; Semrush returned `no_api_units` on every call. The priority tiers in `KEYWORD-MAP.md` are **judgment-based and unvalidated**. Nothing in this document states a volume or a difficulty figure as measured, and neither should anything built from it.

## 1. What actually shipped

A hand-written Node static site generator — `build.mjs` + `templates.mjs` + `content.mjs` + `site-config.mjs` — with **zero runtime dependencies**, emitting `dist/` for Vercel. Not Next.js, not React, not Tailwind. Serverless functions live in `api/` and handle the booking form only.

**22 content routes plus a custom 404 = 23 HTML files.** 21 routes appear in the sitemap (`/thank-you` is `noindex`).

| Group | Routes |
|---|---|
| Home | `/` |
| Services | `/services` + `/services/balayage`, `/services/color-and-highlights`, `/services/haircuts-and-styling`, `/services/hair-extensions`, `/services/hair-treatments` |
| Proof & person | `/portfolio`, `/about` |
| Conversion path | `/new-guests`, `/visit`, `/book`, `/thank-you` *(noindex)* |
| Answers | `/faq` |
| Editorial | `/journal` + `/journal/balayage-vs-highlights`, `/journal/prepare-for-hair-color`, `/journal/hair-extensions-consultation` |
| Local | `/las-vegas-hair-stylist` |
| Trust & legal | `/policies`, `/privacy`, `/terms` |
| Utility | `/404` *(forced noindex)* |

The route list is generated by `pages()` in `templates.mjs`, and `build.mjs` validates it at build time: any invalid route shape, duplicate path, or page missing a title, description or body **throws and fails the build**. A missing home page fails the build. That is a real technical-SEO guardrail most static sites do not have.

**What the architecture buys, in SEO terms:** every page is complete, server-rendered HTML with no client-side hydration and no framework payload. There is no route that requires JavaScript to produce its content. `script.js` handles menu, reveals, the decorative film and form UX — remove it entirely and every page still reads, links and converts. For both classic crawlers and answer-engine fetchers (many of which execute no JS at all), that is the single most valuable property the site has.

## 2. Indexing, canonicals and robots

### The indexing switch — verify this first
`site.indexable` is `env('INDEX_SITE') === 'true'`. Anything else, **including unset**, emits:

```
<meta name="robots" content="noindex,follow">
```

on every page. The local build manifest at `.build/page-manifest.json` currently records `"indexable": false`. **Confirm `INDEX_SITE=true` is set on the production environment of the `beauty-by-kyrin` Vercel project and that a live page's source contains `index,follow`.** If it does not, nothing else in this document matters. This is the highest-priority check on the site.

When indexable, the directive is:
```
index,follow,max-image-preview:large,max-snippet:-1,max-video-preview:-1
```
`max-image-preview:large` matters for a hair site — it permits a large thumbnail in Discover and image-rich results. `max-snippet:-1` permits unlimited snippet length, which is the correct posture for a site designed to be quoted (§6).

### Canonicals
Every page emits `<link rel="canonical">` built from `site.origin` + the route. Origin defaults to `https://www.beautybykyrin.com`, overridable by `SITE_URL`. Vercel's `cleanUrls: true` and `trailingSlash: false` mean the served URL and the canonical match exactly — no trailing-slash duplicate, no `.html` duplicate. `og:url` uses the same absolute URL.

### robots.txt
Generated by `build.mjs` into `dist/`. `User-agent: * / Allow: /`, then thirteen named answer-engine and search agents each given an explicit `Allow: /` — `GPTBot`, `OAI-SearchBot`, `ChatGPT-User`, `ClaudeBot`, `Claude-User`, `PerplexityBot`, `Perplexity-User`, `Google-Extended`, `Bingbot`, `Applebot`, `Applebot-Extended`, `CCBot` — plus the sitemap line. The named groups are redundant against `*` and the code says so; they are an affirmative signal for the operators that read them as one, and a record of the decision.

Crawling is **never** disallowed, even on previews. That is correct and deliberate: `Disallow: /` would stop a crawler fetching the page at all, so it would never see the `noindex`, and a blocked URL can still sit in an index as a bare URL with no content. Previews are excluded by the per-page `noindex`, not by robots.

> **Housekeeping — a real trap.** A stale `robots.txt` sits at the repository root pointing its `Sitemap:` line at `https://beauty-by-kyrin-live.vercel.app/sitemap.xml`. It is **not** deployed (only `public/` is copied, and no `public/` exists), so the live file is the generated one. It should still be deleted, along with the other root-level v1 leftovers — `index.html`, `404.html`, `sitemap.xml`, `llms.txt`, `llms-full.txt` — because the next person to edit "robots.txt" will edit the wrong file. Related: the redundant second Vercel project `beauty-by-kyrin-live` should be removed so it can never serve or be linked as a duplicate of the site.

### Headers and redirects
`vercel.json` ships a strict CSP, HSTS with preload, `X-Content-Type-Options`, `X-Frame-Options: DENY`, `Referrer-Policy: strict-origin-when-cross-origin`, and a `Permissions-Policy`. HTTPS everywhere is a baseline ranking signal and is handled.

Four redirects are configured:

| From | To | Type | Note |
|---|---|---|---|
| `/contact` | `/visit` | 301 | Catches the conventional URL a link or directory will guess. Correct. |
| `/gallery` | `/portfolio` | 301 | Same. |
| `/new-clients` | `/new-guests` | 301 | Same. |
| `/reviews` | `/faq` | **302** | Temporary on purpose — there is no reviews page *yet*. Keep it temporary until there is one, then point it at the real page. |

`X-Robots-Tag: noindex` is applied to `/llms.txt` and `/llms-full.txt`. Right call: those files are for machine retrieval, not for indexing as pages.

## 3. The JSON-LD graph

One `@graph` per page, emitted in `<head>` by `schema()` in `build.mjs`, with stable `@id`s so entities are declared once and referenced everywhere:

| Node | `@id` | Contents |
|---|---|---|
| `HairSalon` | `/#business` | name, url, telephone, email, description, `image` (OG + portrait), `PostalAddress`, `founder`/`employee` → the Person, `areaServed` as seven `City` nodes, `hasMap`, `openingHoursSpecification` |
| `Person` | `/#kyrin` | Kyrin Weidauer, jobTitle, `worksFor` → business, url `/about`, image, `knowsAbout` — the six service topics |
| `WebSite` | `/#website` | url, name, `publisher` → business |
| `WebPage` (or `AboutPage` / `ContactPage` / `CollectionPage`) | `<url>#webpage` | url, name, description, `inLanguage`, `isPartOf` → WebSite, `about` → business, `primaryImageOfPage`, `breadcrumb` |
| `BreadcrumbList` | `<url>#breadcrumb` | Built by walking the path segments and resolving each parent from the real page list — so a breadcrumb can never point at a route that does not exist |
| `Service` | `<url>#service` | On the five service pages only; `provider` → business, `areaServed` Las Vegas; set as the page's `mainEntity` |
| `Article` | `<url>#article` | On the three journal posts; `author` and `publisher` → business, `mainEntityOfPage` → the WebPage |
| `FAQPage` | `<url>#faq` | Only where the Q&A is unique to that page |

### What is deliberately absent, and why it must stay absent

| Omitted | Reason |
|---|---|
| `AggregateRating` / `Review` | **No reviews exist.** `testimonials` in `site-config.mjs` is an empty array, and the code omits the section and the schema together. Fabricating a review violates FTC rules and is grounds for Google Business Profile suspension. Never add one. |
| `geo` (`GeoCoordinates`) | Latitude and longitude are empty in `site-config.mjs` with an explicit `TODO(launch)`: read the exact pin from the Google Business Profile. A guessed coordinate at a shared suite address is worse than no coordinate. Fill it only from the verified GBP pin. |
| `hasCredential` | No Nevada licence number supplied. `license.display` is `false`, so the block is skipped entirely. Never invent a licence identifier. |
| `sameAs` | No social handles supplied. `sameAs` is built by filtering an array of empty strings, so it is omitted from both the business and the person rather than emitted empty. |
| `priceRange` | No price is published anywhere on the site. The code carries a comment explaining that a vague `"$$"` unbacked by a real figure is not an improvement. |
| `openingHours` beyond Mon–Fri 09:00–17:00 | Those are **Venus Salon's** general hours. Kyrin books inside them individually, which is why every page also carries the `availability` sentence. The schema states only what is verified. |

This is the discipline that makes the graph trustworthy, and it is enforced structurally: an empty string in `site-config.mjs` renders as *omitted*, never as a placeholder. Preserve that property in any change.

### One genuine improvement available
`HairSalon` is a `LocalBusiness` subtype, which is right for the physical location. But Kyrin is an **independent practitioner inside someone else's salon**, and the address collision with Venus (see `LOCAL-SEO-GEO-PLAN.md` §1) is the defining local problem. The `Person` node already exists with `worksFor` → the business and `knowsAbout` covering the services. Consider strengthening it: `Person.address` matching the business address, and — once the practitioner Google Business Profile exists — that profile's URL in `sameAs` on **both** the Person and the HairSalon. That is the clearest machine-readable statement that "Beauty by Kyrin" is a distinct entity that happens to be located at a Venus Salon suite. **(inferred: no code change is made by this document.)**

## 4. Internal linking

Links are hand-placed in `templates.mjs` and `content.mjs`, not generated by a plugin. The shape:

- **Header (4 links + CTA):** Services, The work, Meet Kyrin, First visit, then `Let's book`. Mobile adds `Find the salon` → `/visit`. `aria-current="page"` is set for the active route and its children (`current.startsWith(url+'/')`) — so a service page marks Services as current.
- **Footer (11 links):** the five nav destinations plus `/las-vegas-hair-stylist`, `/journal`, `/faq`, `/book`, `/policies`, `/privacy`, `/terms`, plus a `/sitemap.xml` link. Every page therefore links to the local page and the journal hub, which is the cheapest way to give both a baseline internal link profile.
- **`closingCta()`** appears at the bottom of most pages and points to `/book`. Conversion first, crawl depth second.
- **Service ↔ journal, both directions.** Each guide carries `relatedServices` (e.g. `balayage-vs-highlights` → `balayage`, `color-and-highlights`) and renders `.related-links`. Service pages link down to the relevant guide. This is the structure `KEYWORD-MAP.md` §1 requires: commercial intent on the service page, informational intent on the post, with the post passing authority up.
- **Breadcrumbs** are rendered visually *and* in JSON-LD from the same resolved page list.
- **Portfolio → service.** Every entry in the `portfolio` array carries a `service` key, so an image can route a browsing visitor into the commercial page.

**Depth:** every route is reachable in at most two clicks from the home page. Nothing is orphaned. The weakest internal profiles are `/policies`, `/privacy` and `/terms` (footer only), which is appropriate.

**One gap worth closing:** the three journal posts link *up* to services, but the five service pages do not all link *across* to each other. Balayage and colour-and-highlights in particular are the pair readers most often confuse — and the balayage page already contains the comparison table that resolves it. A single contextual cross-link between those two pages would strengthen both. Likewise `/las-vegas-hair-stylist` should be linked contextually from `/visit` and `/about`, not only from the footer, because it is a Tier-1 target.

## 5. Content differentiation — what the competitors do not have

`COMPETITOR-RESEARCH.md` profiles 15 Las Vegas competitors and 6 out-of-market benchmarks. Two content patterns on this site are genuinely rare in that set, and they are the site's strategic assets. They are also, not coincidentally, the two things answer engines quote most readily.

### 5.1 "When this is not the answer" — the `notFor` blocks
Every service in `content.mjs` carries `bestFor` **and** `notFor`. The balayage page says, in the page body:

> "You need to cover grey consistently from the root — balayage deliberately leaves the root area alone, so a root-to-tip colour or a root touch-up is the better fit."
> "You want to go several levels lighter in one sitting from dark, previously-coloured hair. That is colour correction work, and it needs its own conversation first."

Almost nobody in the competitive set does this. It works on three levels at once:

1. **Trust.** A page that tells you to book something else is the strongest credibility signal a service page can carry, and it is the exact opposite of the market's default.
2. **Qualification.** A solo stylist's scarcest asset is chair time. A reader who self-disqualifies before requesting never costs a consultation slot.
3. **Retrieval.** "Is balayage good for grey coverage?" is a real question with a clear answer on this site and a vague answer nearly everywhere else. That asymmetry is what gets a page cited.

**Rule:** never soften a `notFor` entry to make a page read more positively. It is the differentiator.

### 5.2 The comparison tables
Service pages carry a `compare` object rendering a real `<table>` with a `<caption>` — e.g. balayage vs. foil highlights across application, where brightness starts, effect, achievable lift, and grow-out. This is structured, scannable, genuinely comparative content in semantic HTML. Comparison tables are disproportionately likely to be lifted into an answer, and the caption gives the extraction a title.

**Rule:** keep them as real `<table>` markup with a `<caption>`, never as styled `<div>`s. The semantics are the point.

### 5.3 The three content assets the site does *not* yet have
`COMPETITOR-RESEARCH.md` identifies these as the least-contested, highest-intent openings. None exists today:

- **Problem-led pages** — brassy blonde, grown-out balayage, box-dye correction, fine hair that will not hold volume, extensions that caused damage. The highest-intent, least-contested traffic in the category. *Caveat: several of these edge toward colour correction, which is **not** among Kyrin's five confirmed services. Any such page must be written as "what is going on with your hair and what to ask about", routing to a consultation — not as a service offer.*
- **Five of the eight journal posts mapped in `KEYWORD-MAP.md`** have no page: `olaplex-vs-k18`, `tape-in-vs-hand-tied-extensions`, `how-often-balayage-touch-up`, `las-vegas-climate-and-your-hair`, `does-balayage-damage-hair`. These are already keyword-mapped and route-named. They are the cheapest content wins available.
- **A reviews page.** `/reviews` currently 302s to `/faq`. Nothing goes here until real, attributable reviews exist.

## 6. AI search and answer engines (GEO)

The goal is not "rank in AI". It is: **when a model answers a question this site answers well, the site is retrievable, parseable and quotable — and the facts it repeats are correct.** Nothing here promises a citation.

### 6.1 Retrievable
- Complete server-rendered HTML on every route; no JS required to read any page. Many answer-engine fetchers do not execute JavaScript at all.
- Thirteen answer-engine crawlers named and allowed in `robots.txt`.
- AVIF/WebP responsive images, explicit `width`/`height`, lazy below the fold, eager + `fetchpriority="high"` on heroes. Fast pages get crawled more.
- No login, no interstitial, no cookie wall.

### 6.2 Parseable
- The JSON-LD graph gives name, phone, email, address, hours, area served and the service list as structured facts with stable `@id`s.
- `FAQPage` markup where — and only where — the Q&A is unique to that URL. The home, visit and new-guest pages reuse entries from the general set, so marking them up again would publish identical Q&A at several URLs. That restraint is correct and should be preserved.
- Real `<table>` markup with captions; real `<dl>` on `/visit`; `<details>`/`<summary>` for FAQ disclosure with the content in the DOM regardless of open state.

### 6.3 Quotable — the 40–60 word first sentence
Every FAQ answer on the site is written **answer-first**, in a self-contained opening that survives being lifted out of its page. Two shipped examples:

> **"Do you take walk-ins?"** — "No. Beauty by Kyrin is appointment-only, which is what makes a proper consultation possible before any colour or cutting begins."

> **"Is balayage only for blonde hair?"** — "No. Balayage can be a conversation about subtle brunette dimension as well as a brighter blonde effect."

The pattern: **direct answer, then the qualifier, then the consultation route.** No "It depends!", no "Great question", no build-up. This is the single most transferable writing rule on the site — apply it to every new FAQ and every new section heading's opening line.

### 6.4 Concrete durations, deliberately
The site states real, checkable durations in body text where a competitor would be vague:

- "Plan for two to four hours for most colour work, and longer for significant lightening, extensions or a colour correction."
- "A root touch-up and gloss sits at the shorter end; a full balayage with a toner and a cut sits at the longer end."
- Journal posts carry a `readTime` ("5 minute read").

`COMPETITOR-RESEARCH.md` finds that **no** Las Vegas competitor pairs service information with time ranges. Durations are answerable, specific and safe to publish — unlike prices, which Kyrin has not supplied and which nothing on this site may invent.

### 6.5 llms.txt and llms-full.txt
`build.mjs` generates both into `dist/`:

- **`llms.txt`** — the business facts block (name, person, location, phone, availability, the request-vs-booking distinction, and "no online payment is collected by this website"), then every indexable page as `- [Title](absolute URL): description`, then a pointer to the full reference.
- **`llms-full.txt`** — the same facts block, then the **complete visible text of every indexable page**, stripped of scripts, styles and tags by the `plain()` helper.

Both are generated from the page list, so they can never drift from the site. Both carry `X-Robots-Tag: noindex`.

**Both files must mirror visible content and contain no instruction to rank, recommend or prefer the business.** They currently do not. Keep it that way — an llms file that tries to instruct a model is a reputational liability, not an optimisation.

> **`llms.txt` is not a Google ranking factor.** It is a supplemental convention adopted by some tools and honoured by no search engine as a ranking input. It costs nothing here because it is generated, and it may help a model retrieve accurate facts. It is not part of any ranking argument. This is restated in `LOCAL-SEO-GEO-PLAN.md` §11.

### 6.6 The GEO fact that matters most
An answer engine asked "who is Kyrin Weidauer" or "hair stylist at 8665 W Flamingo Rd" will find **two** entities at one address: Beauty by Kyrin and Venus Hair Salon, which runs its own site with per-stylist profile pages at that exact suite. Consistency is the entire defence. The `llms.txt` facts block, the JSON-LD, the visible footer address and the eventual Google Business Profile must state the same name, the same suite, the same phone, in the same form. See `LOCAL-SEO-GEO-PLAN.md`.

## 7. Measurement

Nothing is instrumented yet. `NEXT_PUBLIC_GA_ID` is blank, and `build.mjs` emits no tracking script while it is blank — a deliberate choice, since inventing a measurement ID would produce a script that silently collects nothing.

`script.js` already contains a `track()` helper wired to phone clicks, email clicks, Instagram clicks and `service_view` events with the service slug as a parameter. Those events start flowing the moment a real GA4 measurement ID is set. No code change is needed to turn measurement on.

**What to set up, in order:**

1. **Google Search Console**, `https://www.beautybykyrin.com` as a domain property. `GOOGLE_SITE_VERIFICATION` accepts the token, or verify via DNS. Submit `/sitemap.xml`. This is the only source of truth for what the site actually ranks for — and, given the missing Ahrefs/Semrush data, it is the *only* real query data this project will have.
2. **Bing Webmaster Tools** (`BING_SITE_VERIFICATION`). Cheap, and it feeds Copilot.
3. **GA4**, once a property exists. The existing events then work immediately.
4. **Manual weekly SERP checks** for the Tier-1 terms in `KEYWORD-MAP.md`, from a Las Vegas location or a location-emulated browser, recorded in a simple sheet with the date. Personalised results make casual checking unreliable; a dated log is worth more than an impression.

**The metric that matters is appointment requests**, not rankings. `/thank-you` is a discrete, `noindex`, post-submission URL — which makes it a clean conversion destination the moment GA4 is live.

## 9. Standing rules

1. **Never invent a number.** No price, no licence, no rating, no review count, no coordinate, no years of experience, no measurement ID. `site-config.mjs` renders an empty value as omitted; keep every addition on that path.
2. **Never publish a service outside the confirmed five.** Colour correction, bridal, vivids, keratin smoothing and blowouts are unconfirmed and appear nowhere. They stay in section 6 of `KEYWORD-RESEARCH.md` until Kyrin confirms them.
3. **One primary intent per page.** No two pages share a primary keyword (`KEYWORD-MAP.md` §1). Before adding a page, name the keyword no existing page owns.
4. **A request is not a booking.** Every page that touches the form must preserve that distinction.
5. **Keep SEO files generated.** `sitemap.xml`, `robots.txt`, `llms.txt` and `llms-full.txt` all derive from `pages()`. Adding a route updates all four automatically. Never hand-write one of them into `dist/`.
6. **No doorway pages.** One honest local page. Not a page per suburb.
7. **Rankings are never guaranteed.** Not in a client conversation, not in a document, not in a deliverable.
